# LSP tool reliability and tool capability docs Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make LSP requests recoverable and accurate, and document the capabilities and limits of every tool in one reference.

**Architecture:** Preserve the manager/client/tool split and current four LSP operations. Improve client lifecycle and diagnostic result semantics inside the existing layers, then describe static and dynamically registered tools in `docs/tools.md`.

**Tech Stack:** TypeScript, Node child processes and stdio, Bun test suite, Markdown.

**Spec:** `docs/superpowers/specs/2026-11-16-lsp-tool-design.md`

## Global Constraints

- Keep LSP operations `definition`, `references`, `hover`, and `diagnostics`.
- LSP servers remain user-configured external executables; do not add dependencies.
- Every LSP query continues to require file-scoped permission.
- Keep the tools reference in Vietnamese and clearly separate shipped behavior from plans.

## Review Focus

- Language server exits during a request: later calls must be able to start a replacement client.
- Diagnostics are unavailable before timeout: output must not imply there are zero diagnostics.
- LSP result exceeds the output cap: output must remain parseable JSON and disclose truncation.
- MCP tools are configuration-dependent: docs must not suggest they exist when no server is configured.
- Planned attachment and `@` flows: docs must label them as not implemented.
